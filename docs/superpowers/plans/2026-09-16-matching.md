# Matching — Implementation Plan

**Spec:** `docs/superpowers/specs/2026-09-16-matching-design.md`
**Date:** 2026-09-16
**Repo:** `language_exchange_backend_application` (backend only; no app change)

The spec is the authority. Where this plan and the spec disagree, the spec wins.

---

## Global constraints

1. **Normalization must never shrink the pool.** `toBaseLanguage` returns `null` for
   values it does not recognise — American Sign Language (5 native / 16 learning),
   Hawaiian, Dari, British/Korean/Japanese Sign Language. Those users must keep matching
   exactly who they match today. This is the one way this change can make things worse,
   and it gets its own test in every task that touches a query.
2. **Cantonese is not Chinese here.** `zh`, `zh-Hans`, `zh-Hant` merge; Cantonese stays
   itself (spec §1.5 — ten Cantonese↔Simplified pairs, not one reply). Study content keeps
   the full distinction; this relaxation is for partner matching only.
3. **All four endpoints or none.** The exact-string rule appears four times in
   `controllers/matching.js`. This codebase's recurring defect is one rule living in N
   places and getting fixed in one of them; a partial fix here means two endpoints
   disagreeing about who your match is.
4. **No user-visible feature is added or removed.** Scoring inputs change; the response
   shape does not.
5. Blank-language profiles must never score as a perfect match, whatever the candidate
   filter is (spec §1.4).

## Tasks

### Task 1 — the matching key, as one pure function

New `lib/matchLanguage.js`:

- `matchKey(value)` — `toBaseLanguage`, then collapse `zh`/`zh-Hans`/`zh-Hant` to one key,
  then keep Cantonese distinct. Returns `null` for unrecognised input, exactly as
  `toBaseLanguage` does.
- `equivalentValues(value)` — every raw display string sharing that key, **always including
  the input itself**, so an unrecognised value returns `[value]` and matches what it
  matches today.

The equivalence map is built once at module load from the language catalog, not per
request and not from the database.

Pure, model-free, no DB. Table tests: the Chinese family, Cantonese's separateness, the
sign languages and Hawaiian falling through to themselves, `null`/empty/whitespace,
and case/whitespace variation.

**Done when:** the function exists with tests, and nothing calls it yet.

### Task 2 — `getRecommendations` scores on the key

Replace the three `$eq` branches at `:123-150` with `$in` against
`equivalentValues(currentUser.…)`. Weights unchanged — this task changes *who* matches,
never *how much* a match is worth.

**Done when:** a fixture of the real 1,301-user shape yields **more** perfect pairs than
the exact-string rule, never fewer; a user with an unrecognised language matches exactly
the set they match today; a blank-language user scores zero.

### Task 3 — the other three endpoints

`getQuickMatches`, `findByLanguage`, `getSimilarUsers`, same substitution. Batched as one
task because they are the same edit three times and share one review surface.

**Done when:** all four endpoints agree on who matches whom, asserted by a test that runs
the same user pair through each and compares.

### Task 4 — record impressions durably *(the one that makes the rest knowable)*

New collection: who was shown, to whom, at what score, with the score's components, and
when. Append-only. `controllers/matching.js:88-89` currently reads from a 24-hour cache
key and nothing else, so today nothing survives to be analysed.

Must not slow the response: the write is fire-and-forget, and a failed write never fails a
recommendation.

**Done when:** a recommendation request leaves a durable row per shown user; the existing
`recentlyShown` penalty still works; the endpoint's latency is unchanged.

**This task is listed fourth by dependency and first by importance.** If only one thing
ships, ship this — §2.4 of the spec (reweighting) is unanswerable without it, and every
future matching change inherits the same blindness.

### Task 5 — verify against production, then write down the result

Re-run the spec's measurement after Tasks 2-3 and confirm the live numbers move as
predicted: perfect pairs 7,596 → ~17,936, users with no perfect match 320 → ~267.

**Done when:** the measured result is recorded in the spec. If it does not move as
predicted, that is a finding, not a rounding error — stop and investigate before Task 4.

## Explicitly not in this plan

- **Reweighting.** `languageMatch: 50` stays exactly 50. The spec is explicit that the
  weights cannot be responsibly tuned until Task 4 has run for a while, and changing them
  in the same release as the pairing rule would make both unattributable.
- **Dating vs language exchange.** A real product distinction the scoring cannot currently
  express; it deserves its own spec (spec §3).
- **Reciprocity scoring.** Not modelled today, not added here.
- **Denormalized `nativeBase`/`learningBase` columns.** `$in` against a bounded
  equivalence set needs no migration and no sync-on-save. If profiling later shows the
  `$in` is the bottleneck, that is the escalation — measured, not assumed.
- `controllers/users.js` discovery filters.

---

## Risk

The plan's failure mode is Global Constraint 1: a normalization that quietly drops users
whose language it does not recognise. That is why `equivalentValues` always includes its
own input, why the sign languages are named in the tests rather than left to a generic
"unknown" case, and why Task 5 checks the live number moved the right way before Task 4
builds on it.

Second risk: the Chinese decision rests on 8 and 10 pair samples (spec §1.5). It is the
right call on the evidence available, and Task 4 is what makes it revisitable on better
evidence rather than on a rerun of the same small sample.
